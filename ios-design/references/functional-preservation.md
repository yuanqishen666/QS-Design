# 功能保真：设计升级不能把产品做少

## 先建立功能合同

已有项目的代码、产品说明、截图、接口字段和测试共同定义当前产品。开始画图前在内部整理一份最小功能合同：

```text
顶层入口：用户从哪里进入
页面：有哪些真实页面或内容区
主要动作：每页能做什么
关键状态：默认、选择中、展开、完成、空、失败等
业务语义：哪些入口必须分开，哪些修改必须保存
流转：进入 → 操作 → 确认 / 取消 → 返回 / 完成
```

用户没有要求改变的内容一律视为保留。视觉改造可以重新安排层级和容器，但不能通过不画、藏得找不到或改成一条 Toast 来代替原功能。

## 功能覆盖与方向差异是两件事

每个设计方向必须承载同一份功能合同。方向可以改变：

- 哪种内容成为视觉主角；
- 用户如何理解今天的任务；
- 首页如何组织注意力；
- 进入详情时对象如何连续展开；
- 色彩、排版、材质、图像和运动性格。

方向不能改变：

- 已有页面是否存在；
- 学习与复习等已经明确分开的业务入口；
- 保存、取消、返回和完成的含义；
- 用户给定的数据关系和必要状态。

首页、学习页、复习页是同一产品的不同页面，不是三个设计方向。不同方向应先在同一个代表页面或同一个任务起点上可比较，再分别延伸到自己的关键交互时刻。

## 从页面清单变成可走流程

为原型建立一个很小的状态图，不需要交付给用户：

```text
首页
├─ 主要任务 → 流程页 → 结果 / 完成 → 首页
├─ 次要任务 → 对应页面 → 返回
├─ 搜索 / 列表 → 详情 → 收藏 / 操作
└─ 设置 / 计划 → 修改 → 保存或取消 → 首页更新
```

顶层 Tab、分段控件和首页主要入口都应到达真实页面。页面里的返回、保存、取消、揭晓、筛选、收藏或切换要改变可见状态，而不是只弹一句“已点击”。

## 局部设计任务

用户只要求一个页面时，不必凭空实现整个 App，但这个页面已经出现的入口必须有合理去向；与现有工程相连时，沿用真实路由。若用户要求“页面设计”且项目中同一功能已有多个相关页面，默认把核心路径一起做成可点击原型，而不是只画一张孤立截图。

## 完成设计时守住三件事

1. 功能合同中的页面和入口没有凭空消失。
2. 方向差异来自视觉与交互解释，不来自各拿一个不同功能充数。
3. 用户从样板图进入后，能实际走到主要功能页并返回。
