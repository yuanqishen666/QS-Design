# 任务胶囊与上下文隔离

设计任务是上下文根，项目只是可选事实源和存储位置。纯聊天默认使用临时 Task Capsule，不要求目录、仓库或产品文档。

## 上下文类型

- 业务事实：当前任务内可复用。
- 当前要求：当前任务内可复用。
- 模型假设：只属于当前候选，除非用户确认。
- 候选设计：只属于候选分支，不能自动继承。
- 用户决定：只按用户明确作用域继承。

## 候选关系

| 意图 | 关系 | 读取内容 |
|---|---|---|
| 新做、换方向 | fresh-root | 业务事实和当前要求 |
| 继续某版 | continue-parent | 点名父版本及当前事实 |
| 保留指定方面 | aspect-inheritance | 只读点名方面 |
| 融合点名版本 | explicit-merge | 只读点名版本的点名方面 |
| 保留功能重来 | soft-reset | 默认仅业务事实、平台目标和明确排除项；其他内容逐项再授权 |
| 完全忽略前面 | hard-reset | 仅逐项再次确认的事实、要求和强制约束 |

`rejected` 与 `archived` 候选永远不可作为父版本。`shown`、`superseded` 只有被用户点名时才可读。已选择或已实现版本也不能因为“最新”而自动进入上下文。

`aspect-inheritance` 只允许一个父候选；`explicit-merge` 至少两个父候选，并为每个父候选分别列出方面。候选以 `aspect_refs` 标出方面产物。工作器不仅得到引用名，还必须得到这些授权引用对应的内容；任一内容缺失时失败，不得改读整份原型。

Task Capsule 的 `read_policy` 是所有运行的权限上界。profile 项即使已获保存同意，也默认不进入任何新任务；只有当前 Task Capsule 在 `allowed_profile_context` 中点名后才能读取。

## 物理隔离

新根方向必须使用不继承聊天历史的设计工作器或等价隔离。协调器先编译 `context-manifest.json`，工作器只能得到由其编译出的哈希 payload。旧截图、源码、方向解释和视觉指纹不得出现在 fresh-root、soft-reset 或 hard-reset 的生成输入中。子进程的 stdin/环境隔离不等同于操作系统文件沙箱；涉及本地工作器时还需宿主提供独立工作目录与文件系统隔离。

生成后可由独立检测器判断新结果是否与拒绝稿过度相似，但旧视觉细节不能返回给生成工作器。用户要求完全不读取旧稿时关闭该检测。

## 反馈作用域

默认 `candidate`。只有用户明确表达“接下来”“这个产品”“以后”时才分别提升到 task、project 或 profile；profile 必须明确同意。模糊反馈如“太 AI”“太普通”只说明当前候选未达预期，不能被改写成永久元素黑名单。

## 透明说明

每次重置或继承时，用一行说明：本次保留什么、不读取什么、父版本是什么。说明不是额外审批门，只用于让用户校正上下文。
