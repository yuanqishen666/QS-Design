# 所有参考与已实现内容的事实边界

用户给出的任何参考，以及任务范围内任何已经实现的内容，都只能用于确认“有什么功能、业务怎样运转、数据怎样流转、接口怎样约束”，不能提供新页面的结构或样式。无论来源是截图、设计稿、原型、App、网站、其他平台、竞品、代码仓库、当前产品还是历史版本，事实提取和界面设计都必须隔离。

## 允许提取的内容

- 产品需求、功能说明、接口文档、OpenAPI、请求与响应类型。
- service/repository、领域模型、状态机、权限、错误码、缓存和持久化规则。
- 测试用例、路由目的、入口条件、动作结果和前后端契约。
- 业务术语、必须保留的用户可见字段及真实示例数据。

把结果整理成不含版式的功能清单：用户目标、触发条件、输入、输出、业务状态、失败与恢复、相关接口、必须保持的不变量。

## 不得带入新设计的内容

- 任何参考或已实现内容中的页面模板、组件树和页面骨架。
- 任何参考或已实现内容中的 CSS/样式、设计 token、色板、圆角、阴影、间距和排版参数。
- 截图、录屏、设计稿或原型中的卡片形态、分区顺序和 CTA 位置。
- 参考页面如何拆屏、分组、排序、导航或逐步披露功能。
- 参考页面的动效编排、手势结构、图标处理和视觉装饰。

同一文件同时包含业务代码和页面代码时，只读取能证明接口、状态与结果的逻辑部分；不要把模板和样式纳入设计上下文。功能无法从契约、类型、测试或服务层确认时，可以最小化查看事件处理逻辑，但只记录业务动作与结果，不记录控件、位置、分组或页面流。

## 业务流程不等于页面逻辑

必须保留的是“用户做什么后产生什么业务结果”，例如保存计划后后端返回新的每日目标。需要重新设计的是“入口放在哪里、经过几屏、用 Tab 还是卡片、先展示什么、如何操作和反馈”。接口契约不能被当作复制页面结构的理由。

## 品牌与视觉资产

参考或已实现页面的样式不能自动升级为品牌规范。只有独立维护的官方品牌资产或用户明确指定的品牌规范可以作为三方向共同约束；即使保留品牌，三套方向仍须在信息架构、操控模型和视觉材料上独立。不得从参考页面或产品实现的 CSS 反推品牌色与组件规则。

## 已选方向的后续迭代

只有用户已经从本 skill 输出的三方向中明确选定某个版本后，后续迭代才可读取这一份已批准父版本；不得顺带读取其他参考、旧稿或已实现页面的 UI。用户说“参考这个”“看当前实现”“照着已有功能做”“对接现有接口”都只授权提取功能、业务逻辑和契约。

## 交付证据

新设计的 `directions.json` 必须声明：

- `source_boundary.mode` 必须为 `function-contract-only`。
- `fact_sources` 列出实际用于提取功能、业务逻辑或契约的所有参考和实现来源。
- `excluded_ui_sources` 列出其中已隔离的页面结构、样式、截图、设计稿、原型或旧设计目录。

声明不能代替行为，但缺失声明时不得进入待评审状态。
