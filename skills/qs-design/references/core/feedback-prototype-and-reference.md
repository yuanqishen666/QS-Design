# 反馈增量、原型与参考蒸馏

## Feedback Delta

用户否定或调整候选时，不把一句审美反馈直接扩张成设计系统规则。进入下一工作器前，记录：

- 用户原话和观察到的问题；
- 用户希望获得的结果；
- 推测原因与置信度；
- 必须保留和本轮改变的内容；
- 本轮不得额外推断的内容；
- 下一次只验证的假设、变化范围、预期观察和证据；
- 建议使用继续、方面继承、融合、软重置还是硬重置；
- 软/硬重置是否有用户明确授权。

低置信度诊断只能做 targeted 或 representative-flow 实验，除非用户明确授权全产品重置。`太 AI`、`太普通` 等反馈默认只说明当前候选失败，不能产生全局元素黑名单。

## Prototype Contract

在制作产物前声明保真度：

- `specimen`：比较一个代表任务的设计机制；
- `static`：证明静态构图和内容；
- `clickable`：证明状态变化和可点击路径；
- `native`：证明平台原生能力与行为。

合同同时冻结必测路径、状态、数据 fixture、视口或设备，以及所需证据。Clickable 至少需要最终渲染、真实运行路径、逐步捕获和 assertion report；静态图不能证明可点击流程，HTML 不能证明原生触觉或系统通知。

内部视觉修正使用 `render → inspect → diagnose → targeted correction → rerun`。默认最多两轮；达到上限后带着证据交给用户判断，不继续无止境自我润色。

## Presentation Gate

视觉产物的生命周期是 `planned → rendered → inspected → presented`。`rendered` 只说明文件存在，`inspected` 只说明完成了工艺检查；只有最终回复实际把 preview 展示给用户，才能记录为 `presented`。

Presentation Record 至少记录工作模式、状态、全部产物引用、已内嵌 preview、可打开体验入口、展示通道、展示时间或阻塞原因。正式设计遵循以下门槛：

- `design`、`interaction-lab` 和带视觉改造的 `implementation` 必须展示至少一个 preview；纯 `audit` 可以是 `not-applicable`；
- 每个正式方向都要有可直接查看的 preview，不能只展示其中一个方向；
- `clickable` 或 `native` 除 preview 外还必须提供可打开的体验入口；
- Markdown 表格、ASCII 线框、文字布局说明、组件清单和仅有文件路径都不算 preview；
- preview 与体验入口必须引用本轮真实产物，不能引用计划、源码路径或验证报告冒充结果；
- 没有展示通道时记录 `blocked` 和恢复动作，不把文字建议标成已交付设计。

独立原型位于会话或临时输出位置，不会修改产品源码，因此不需要候选批准。用户批准控制的是源码接入；不得把“未批准实现”误解为“不得制作或展示原型”。

## Reference Synthesis

每个外部来源只蒸馏可解释的机制：观察到什么、对用户产生什么作用、服务当前哪项业务需要、在本地改写成什么规则、哪些独特表达绝不复制、适用约束和独立业务/平台/第二来源依据。

当同一来源同时控制布局、排印、图像、材料与标志交互时，视为页面级模仿风险。拆开机制或寻找独立依据，不能用“灵感”掩盖整体复制。
