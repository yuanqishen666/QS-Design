# SwiftUI 交付：原生行为与可运行入口

用户批准原型并要求 SwiftUI、真实 iOS 能力或接入原生工程时读取。一般视觉探索先用隔离 HTML 或原生 sample；批准前不得修改产品工程。

## 实现前门禁

先用 `design-run.mjs require-approved` 验证批准版本与原型哈希，通过后运行 `start-implementation` 再改产品源码。没有批准记录、批准版本不明确或原型在批准后发生变化时停止实现，回到原型评审。实现中的技术细化可以直接完成；信息架构、用户可见文案、视觉方向或标志性动效发生变化时更新原型并重新批准。验证完成后用 `finish-implementation --evidence "验证证据"` 记录交付结果。

## 沿用项目

读取应用入口、导航、主题、状态管理和与任务最接近的页面。沿用最低系统版本、依赖及目录，新增能力先确认目标版本支持；不另建平行设计系统或重写无关页面。

没有现有项目时创建最小可运行 SwiftUI 原型，使用贴近任务的本地演示数据和真实状态。组件按功能边界拆分，抽象只为重复行为或清楚的数据关系服务。

## 用原生能力承接熟悉行为

适合时使用 `NavigationStack`、`TabView`、`sheet`、`Menu`、`List` 和系统输入，保留返回、键盘、文本选择与辅助功能。自定义容器承载产品独特内容，平台控件的位置、密度与上下文仍由设计决定。

展开、拖动、选择和完成由状态驱动，支持新输入接管。需要临时编辑时建立草稿，保存提交，取消保留原值；不要用 `DispatchQueue` 串联业务流程。浮层策略见 [临时界面](patterns/transient-surfaces.md)。

品牌字体、颜色、图形与 SF Symbols 按实际需要使用。原生触觉可在有意义的时刻实现，考虑减少动态效果、文字大小和 VoiceOver；相关 API 与系统样式以目标版本资料为准。第三方库可以在许可、兼容性和项目依赖合适时复用，不要求为了原创重复造轮子。

## 范围与真实结果

主要入口进入实际页面或状态，详情对应同一对象，选择与筛选影响内容，编辑保存后可重新查看，返回保留合理上下文。只实现本次任务真实需要的状态；无异步或权限功能时不额外制作网络失败、权限等页面。

多方向使用共同任务和数据，各自拥有状态实例与独立主题。双模式是否交付取决于用户要求、现有产品和场景；范围内的页面与弹层保持一致。

原型数据和能力边界要清楚：页面里的提醒记录不会自动成为系统通知；没有实现定位、通知或持久化时，不用文案假称已经完成这些动作。

## 提供实际运行方式

- 现有工程：只在原型批准后进入项目完成请求范围，使用项目可用构建或运行方式，并指出进入对应功能的路径。
- 独立概念：提供可运行工程及明确入口；环境能启动模拟器或预览时直接打开，说明实际验证到的范围。
- 普通用户希望点击体验：确认交付入口是否真的可用。Xcode Preview 或源文件说明是开发者运行方式，不能称作已可在浏览器或手机直接打开的分享链接；需要浏览器体验时可另提供适当 HTML 原型，并说清能力差别。
- 用户明确只要静态设计：按其范围提供画面，无需扩成工程。

默认可操作交付不能退回“几张状态图加交互说明”。封面从实际运行画面捕获；无法运行的部分如实说明，不能以代码存在代替运行成功。原生源码、模拟器体验和已发布 App 是不同交付状态，不把上架或部署扩成普通设计任务。

实现素材、组件和动效入口见 [来源入口](source-registry.md)，视觉范围见 [审美系统](aesthetic-system.md)。
